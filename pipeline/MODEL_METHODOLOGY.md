# Model methodology (pinned constants for fit_models.py, P4)

`fit_models.py` doesn't exist yet (it's P4 scope) but its fit methodology is pinned here in Phase 1, in machine-readable form in `model_constants.json`, so that later drift-audits (spec Section 11.3) measure real data drift rather than ambiguity about *how* the fit was done. Changing any of these constants is a deliberate methodology change, not a routine data update, and should be called out explicitly in a commit message and `PROGRESS.md`.

## Power law corridor (spec Section 8.1)

Model: `log10(price) = a + b * log10(d)`, where `d` = days since Bitcoin's genesis block (`2009-01-03`).

- **Fit start date: `2010-07-17`.** Price data before this is thin/illiquid (pre-exchange era); the spec itself says "full history from ~2010-07 onward." Fixed here so the fit window can't silently drift.
- **Sampling: daily, no downsampling.** Every row in `price_daily.json` from the fit start date onward is used, except rows flagged `carried_forward` (a repeat of the last real observation, written under a fresh date during a source outage) — those are excluded from this and every other model in `fit_models.py` (cycle overlay, Mayer, 200WMA) so a data-fetch failure never quietly inflates `n_points` with fabricated observations.
- **Weighting: unweighted OLS.** Plain ordinary least squares in log-log space, equal weight per daily observation. This is a real methodology choice, not a neutral default — `log10(d)` compresses over time, so a year of recent data occupies far less x-axis span than a year from 2011 while contributing the same number of points, meaning recent history has outsized influence on the fit. Pinning "unweighted" here means that effect is a known, stable property of the method, not something that changes if a future session quietly reaches for a different weighting scheme.
- **Expected range** (`model_constants.json` → `power_law.expected_range`): `b ≈ 5.7–5.9`, `a ≈ −17.0 to −16.5`, `R² ≥ 0.95`, consistent with the publicly published Santostasi power-law fits. This is a sanity band for the *fit process*, not a target to reverse-engineer into.
- **Audit drift thresholds** are intentionally wider than the expected range: `b` triggers a WARN only outside `[5.4, 6.1]` (not right at the expected-range edges), because a single bad data point among ~5,800+ daily observations has negligible leverage on `b` — the audit's job is to catch bulk data corruption or a broken fit script, not to enforce the reference range as a hard gate. `R²` drop >0.01 day-over-day, or `b` moving >0.5% day-over-day, are the other drift signals (spec Section 11.3).
- **Bands (±1σ, ±2σ) are descriptive envelopes, not confidence intervals.** Log-price residuals here are heavily autocorrelated across multi-year cycles, so standard confidence-interval interpretation doesn't apply — site copy must never call them "confidence bands."

## 4-year cycle overlay (spec Section 8.2)

Halving dates and the next estimated halving are pinned in `model_constants.json` → `cycle_overlay`, sourced from the spec: `2012-11-28`, `2016-07-09`, `2020-05-11`, `2024-04-20`, next at height 1,050,000 (~2028-04).

## Cycle tops (owner request, 2026-07-26; Fable director ruling on presentation)

**What this is not, first:** this is *not* a second power-law curve fit through Bitcoin's historical cycle-top prices. That approach was evaluated and explicitly rejected — see `IMPROVEMENT_BACKLOG.md`'s 2026-07-26 entry for the full analysis. In short: a curve fit through only 5-6 points is exactly the "crude by design, few data points" pattern this project already cut once (the Deviation Dial, see CLAUDE.md Section 1); leave-one-out sensitivity on that fit swung 2035 projections by up to 2.7x depending which single top was dropped; out-of-sample walk-forward testing (fit on tops known at time T, predict the next one) missed by −56% to +202% across every testable historical case; and it does not even deliver "more conservative" — compared to this site's own Cruise trend it actually sits *above* it (only reading as conservative against Redline). Shipping that would be a real rigor mismatch for a site whose stated differentiator is radical transparency.

What ships instead needs no new curve and no extrapolation: historical cycle tops are scored against the power-law fit that already exists (the same `a`, `b`, `sigma` behind Idle/Cruise/Redline), reporting how many sigma above that trend line each one landed. Director ruling (Fable, 2026-07-26): the marker set must be admitted only by a *stated, mechanical* rule, never hand-picked, or this becomes exactly the curation problem the analysis above rejected. Three rules run, and their results are unioned rather than collapsed to one "the" top per era — where two rules disagree about the same halving era, both points ship, labeled, rather than the disagreement being resolved by fiat:

- **(i) Confirmed cycle tops — ZigZag swing method**, `identify_cycle_tops()` in `fit_models.py`, run over the full `price_daily.json` series (not just the power-law fit window). A running high is confirmed a **cycle top** (`kind: "confirmed_top"`) once price later falls `cycle_top_drawdown_confirm_pct` (0.70) from it; a running low is confirmed a **bottom** once price later rises `cycle_top_recovery_confirm_pct` (0.50) from it, resuming the search for the next top. These two thresholds are pinned in `model_constants.json` → `power_law` and were chosen because together they reproduce the canonical list of major Bitcoin cycle tops with zero hand-picking — changing either is a methodology change, not a routine data update (same rule as the power-law fit constants above). `identify_cycle_tops()` itself knows nothing about halving eras — it returns pure ZigZag facts (`date`/`price`/`confirmed`); `compute_cycle_tops()` is what layers era membership and the drawdown figure on top (see below), specifically so those two concerns can't drift out of sync with each other again the way an earlier version let them.
- **The unconfirmed remainder of (i)** — the ZigZag algorithm's own currently-tracked running high, whatever its date — is `kind: "current_era_high"` when that date falls in the still-open era, or `kind: "unconfirmed_top"` when it doesn't (an old high, sitting in an already-closed era, that simply hasn't fallen 70% yet). These are deliberately different labels: "the current era's own high so far" and "an unconfirmed top left over from a previous era" are different facts, and collapsing them into one label previously let an old, closed-era high render as if it described the live one.
- **(ii) Each halving era's own peak sigma-vs-trend excursion** (`kind: "era_max_sigma"`), computed over the same five eras `compute_cycle_overlay` already defines (pre-first-halving, then one per halving in `cycle_overlay.halving_dates`, then the current open era) — added only when that date isn't already admitted by (i) for the same era. This is what surfaces real disagreements like "this era's drawdown-confirmed top isn't the date it actually ran furthest above trend" instead of silently picking whichever one a human would have reached for.
- **(iii) The current, still-open era's highest CLOSE (raw price, not sigma) to date** (`kind: "current_era_high"`), added only when that date isn't already admitted above. The current era hasn't had a chance to produce a drawdown-confirmed top yet, almost by definition — omitting its running high would silently exclude the most recent, most relevant data point.
- **`confirmed` is true only for a settled fact**: a genuine ZigZag-confirmed top (i), or an `era_max_sigma` point (ii) from an era that has already closed (a later halving has since happened). It is false for anything about the current, still-open era, and for any `unconfirmed_top` regardless of era — that high could still be exceeded, and the site's own carried-forward/STALE conventions already establish that in-progress facts get shown, clearly labeled, not hidden. **Every `confirmed: false` entry carries `drawdown_so_far_pct`** (`(1 - latest_price/this_price) * 100`, rounded), computed once, uniformly, in `compute_cycle_tops()` regardless of which rule admitted the point — an earlier version computed this only on the ZigZag path, which could render a missing-value placeholder for an era-loop-admitted point; schema-enforced now (`cycle_tops` items: `confirmed:false` implies `drawdown_so_far_pct` required).
- **Scoring: no new fit.** For a point at day-offset `d` with price `p`, `sigma_vs_trend = (log10(p) - (a + b*log10(d))) / sigma`, using that same day's `a`/`b`/`sigma` from the power-law corridor fit above. A point with `sigma_vs_trend` near the corridor's own `+2σ` Redline band topped right at the ceiling.
- Output lands in `data/models.json` → `power_law.cycle_tops`, schema-documented in `models.schema.json`. Refit nightly like everything else here — none of it is hardcoded in `charts.js`.
- **`power_law.cycle_top_era_maxima_sigma`** (`cycle_top_era_maxima()` in `fit_models.py`) is each halving era's own highest `sigma_vs_trend` value **and the date it occurred**, oldest first, current era last — `{date, sigma_vs_trend}` pairs, not bare numbers: an era's confirmed top and its own peak-sigma reading can fall on different days (the real committed history already has this — 2013's confirmed top is 2013-12-05, but 2013-11-30 actually ran slightly further above trend), so the date has to travel with the value rather than being borrowed from some other entry. This exists so site copy can say "each cycle topped lower than the last relative to trend" *only when that's still actually true* (checking the `sigma_vs_trend` sequence is non-increasing) and can correctly cite *when* the cited value happened, rather than asserting either as a permanent law or guessing the date.

## Model honesty (Phases A–D, owner-approved 2026-10-01)

A walk-forward backtest of this site's own power-law corridor (refit on the first of every month since 2013 using only data available before that date, then scored against what price actually did) found the trend line has real long-horizon skill, but the original presentation overstated its precision. These changes are deliberate methodology changes, pinned in `model_constants.json` → `honesty`:

- **Bands are empirical residual quantiles, not ±2σ.** Idle/Redline are the trend shifted by the 2.5th/97.5th percentiles of past fit residuals (log10 space); a new inner band uses the 16th/84th. The real residual distribution is skewed (long upside tail): the old symmetric ±2σ floor sat far below anywhere price had been (only ~0.6% of history below it). `sigma` is still computed and still drives `z_score` and cycle-top `sigma_vs_trend` readings, unchanged.
  - **Rejected:** bands whose width decays with time. Cycle peaks above trend have shrunk every era (+4.0σ → +0.5σ), but projecting that decay forward was overconfident in walk-forward testing (~77% realised coverage for a nominal 95% band). The decay is reported, not extrapolated.
- **Trend uncertainty (projection fan)** is a circular moving-block bootstrap of residuals (730-day blocks preserve the multi-year autocorrelation; 300 replicates; fixed seed so the nightly refit is deterministic). Published as `trend_uncertainty` (5th/50th/95th percentile of the trend itself, log10) and `trend_low`/`trend_high` per projection. This is parameter uncertainty in the line, separate from the bands' spread around it.
- **Point-in-time z (`realtime_z`)**: on each month start since 2013, refit on prior data only and score that day. Historical z-scores computed with today's fit look more predictive than they were (rank correlation with next-year return −0.70 in hindsight vs −0.52 point-in-time).
- **Short-term path (`short_term`)**: trend + AR(1) mean reversion of the residual (sampled every 30 days; half-life ≈ 160–175 days), published only for 12 monthly steps (≈1 year). It roughly matches a random walk at 90 days and adds nothing beyond a year, which is why it stops there.
- **Recent-window scenario (`scenario`)**: an independent OLS fit over data since 2017 (b ≈ 4.8 vs 5.6 full-history). A counter-reading for "diminishing returns", shown beside the main fit rather than replacing it; its walk-forward record is in `data/backtest.json` → `scenario`.

Evidence lives in `data/backtest.json` (recomputed nightly by `pipeline/backtest.py`) and the append-only live ledger `data/forecasts.json` (one frozen forecast per calendar month; only `outcome` is filled in later). `audit.py`'s `forecast_calibration` check warns if 1-year walk-forward band coverage falls below 80%, the backtest goes stale, or matured ledger forecasts miss the band more than 25% of the time.
