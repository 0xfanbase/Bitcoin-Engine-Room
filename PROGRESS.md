### 2026-07-13 — Fable-led data pipeline + health-check audit, 8 real bugs fixed

Owner asked for a Fable-led audit of the data pipelines and health check specifically (not a UI/creative review this time). Did my own first pass through `fetch_snapshot.py`/`audit.py`/`validation.py`/`sources.py`/`daily.yml` and formed candidate findings, then ran an independent Fable-model agent (Agent tool, `model: "fable"`) as a technical auditor with that context plus the mandate to independently verify or refute each candidate and find anything else. Six of my candidates got a verdict (4 confirmed, 2 refuted with reasoning); the agent's own top finding was the most severe bug of the round. All fixes verified against `pytest pipeline/tests -v` (119/119, up from 117 -- 2 new regression tests) and a real `python -m pipeline.audit --dry-run` (still PASS).

- **Most severe, Fable's own find**: fallback sources that read their own date from upstream data -- `blockchain.info`'s hash-rate chart (can lag a day) and alternative.me's Fear & Greed "latest" reading -- had no check that the candidate's date actually advanced past the last committed row. A lagging fallback got appended as a second, duplicate/out-of-order-dated row straight into committed history, and kept re-corrupting it on every subsequent run while the primary source stayed down (the idempotent same-day skip never matches a date that isn't literally today, so it never caught up). Fixed with a new `_is_stale_or_duplicate_date()` guard in `snapshot_metric()` (`fetch_snapshot.py`) that rejects such a candidate as a chain failure instead of accepting it -- new regression test mocks a lagging blockchain.info hash-rate response and confirms it's rejected and carried-forward instead of duplicated.
- **`daily.yml` had no `timeout-minutes`** (confirmed my own candidate) -- `ci.yml` got this guard back on 2026-07-09 after a real ~15min hang, but the daily pipeline job was never given one; an unguarded hang burns up to GitHub's 6h default. Added `timeout-minutes: 15`.
- **A downstream `fit_models`/`audit` crash silently discarded a whole day's already-fetched, already-valid snapshot data** -- `daily.yml`'s commit step only ran if every prior step succeeded, so a crash two steps later than the actual data fetch meant the new history rows + health.json were never committed, with no mechanism to backfill the missed day (a permanent continuity gap). Gave the snapshot step an `id`, changed the commit step to `if: always() && steps.snapshot.outcome == 'success'` -- now a snapshot's real data survives even if refitting/auditing crashes afterward, while the job still reports failure so the crash itself doesn't go unnoticed. Added a `concurrency: {group: daily-snapshot}` guard in the same pass to rule out an overlapping cron + manual `workflow_dispatch` race corrupting a mid-write commit.
- **Carried-forward rows misrepresented their own provenance** (confirmed my own candidate) -- when every source in a chain fails, the carried-forward row keeps its *original* `source` tag under *today's* date, so a reader of e.g. `price_daily.json` alone (without cross-referencing `health.json`, whose STALE flag is transient and clears on recovery) would see a stale repeat attributed as if freshly observed. Added an optional `carried_forward: true` field, set only on the carry-forward path in `fetch_snapshot.py`; extended all 5 history schemas (`pipeline/schemas/*_daily.schema.json`) to allow it.
- **`--metrics` subset runs wiped every other metric's health.json record** -- `run_snapshot()` built `new_health["metrics"]` from scratch each run and overwrote the whole file, so `--metrics price_daily` would delete hashrate/difficulty/supply/fng's records and, via the "all OK -> auto-close outage issue" check evaluating only the processed subset, could wrongly close a real open outage issue for a metric the run never touched. Now seeds `new_health["metrics"]` from `prior_health` and only overlays the metrics actually processed. Harmless in practice today (`daily.yml` always runs the full set) but a real footgun in the CLI's own documented `--metrics` flag.
- **Cross-source price check re-fetched sources already fetched (or already known-failed) moments earlier in the same run** (confirmed my own candidate) -- `_check_price_cross_source()` took `row` as a parameter but never used it, unconditionally re-fetching both mempool.space and CoinGecko even when the primary chain had *just* used one of them as the winning source. Worse, when the chain fell through to CoinGecko *because* mempool.space failed, the cross-check re-ran mempool's full retry/backoff cycle against a source known-dead seconds earlier. Now reuses `row`'s value for whichever source it actually came from -- saves up to 2 redundant HTTP calls/day, honoring the polite-client hard rule (CLAUDE.md Section 4).
- **`check_sanity_replay` silently skipped a missing history file** while `check_continuity` FAILs on one -- but `difficulty_daily` is deliberately exempt from continuity (its P1 portion is a real sparse step function), so a deleted/missing `difficulty_daily.json` would previously produce *no audit finding at all*. `check_sanity_replay` now FAILs on any of the 5 metrics' history file being missing.
- **`hashrate_daily.schema.json` allowed `value: 0`** (`minimum: 0`) where price/difficulty already require `exclusiveMinimum: 0` -- tightening it to match surfaced a real, previously-invisible data bug: the committed `hashrate_daily.json` actually had five `0.0` placeholder rows (2009-01-04 through 2009-01-08), the exact ~6-day no-blocks-mined gap immediately after genesis already documented for `supply_daily` in `known_gaps.json` -- blockchain.info's hash-rate estimator had no block interval to compute from during those days, same root cause, never caught because hashrate was never added to `backfill.py`'s existing price/difficulty zero-filter. Fixed at the source (`backfill.py` now filters hashrate too), patched the 5 rows out of the committed file directly (surgical, not a full network re-backfill), and added the matching `known_gaps.json` entry with the same citation as `supply_daily`'s.
- **Refuted, no fix needed**: (a) carried-forward rows bypassing schema/sanity validation -- safe by induction, since only the `date` field changes and it's always today/ascending; (b) `check_hashrate_live`'s empty-history accept-all branch -- schema validation already rejects negatives before the sanity check runs, and 15+ years of committed history means the branch is unreachable in practice; (c) `check_model_drift`'s `if b_prev:` truthiness check -- a real fitted `b` is never exactly 0, so this is also the function's own divide-by-zero guard, not a bug.
- **Logged to `IMPROVEMENT_BACKLOG.md`, not fixed this round** (judgment calls, not concrete bugs): a long-enough outage can make `check_price_live`'s 40% day-over-day bound reject every real recovery value forever (perma-STALE, needs a human); `subsidy.py`'s `NEXT_HALVING_HEIGHT` is a dated constant that will read 0 forever after the ~2028 halving until manually bumped (also duplicated in `assets/app.js`); `pipeline/requirements.txt` pins nothing (`>=` only), so a breaking dependency release lands directly in the next daily run.

### 2026-07-13 — Mobile UI/UX + code review, biggest wins implemented

Owner asked for a Fable UI/UX + code review focused specifically on mobile performance (they use the site mostly on mobile). - **The big one**: `app.js`'s `boot()` was fetching all 5 `data/history/*.json` files (~3MB combined) on every page load before dispatching `ber:booted` -- the event every other module (live.js's WebSocket/polling, charts.js, health.js) waited on. Three of those five files (`hashrate_daily.json`/`difficulty_daily.json`/`supply_daily.json`, ~2MB) were fetched in full but only their *last row* was ever read anywhere in the code. Fixed at the source: `pipeline/fetch_snapshot.py` now writes a `last_date`/`last_value` digest (`last_classification` too for `fng_daily`) into each metric's `health.json` record, mirroring the existing `tip_height` precedent exactly -- new `_latest_fields()` helper, schema updated, 3 pipeline tests extended, `data/health.json` regenerated from the already-committed history files (no live network call). `app.js` now paints every gauge straight from `health.json` (already the first thing it fetches) and dispatches `ber:booted` immediately, no longer gated on any history download at all.
- **charts.js decoupled from boot entirely**: it now fetches its own data (`models.json`, `price_daily.json`, `fng_daily.json` -- the only two history files anything actually charts) and lazily injects the ~340KB(gz) ECharts CDN script via an `IntersectionObserver` on `#power-law-card` (`rootMargin: "600px 0px"`), instead of both loading unconditionally on every visit regardless of whether the user ever scrolls to Price Models. Removed the eager `<script src=".../echarts.min.js">` tag from `index.html`. Partial fetch failures (e.g. `models.json` OK but `price_daily.json` down) still render whichever charts don't depend on the failed one, matching the site's existing failover philosophy.
- **`rain.js` mobile hygiene**: `draw()` was calling `getComputedStyle()` every frame (20x/sec, forever) purely to re-read CSS custom properties that never change on a single-theme site -- now cached once in `start()`. `resize()` reassigned `canvas.width/height` from `window.innerHeight` on every `resize` event, which always wipes the canvas bitmap -- and mobile browsers fire `resize` with a 50-100px height-only delta every time the URL bar collapses/expands on scroll, so the rain was visibly blanking and rebuilding on the single most common mobile gesture.
